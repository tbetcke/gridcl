## Scope summary

M5 adds gridcl's VTU writer (XML `version="2.2"`, appended raw or base64 binary, optional zlib) with linear cells for p = 1 and VTK Lagrange cells (68–73) for p ≥ 2, user point and cell data, the PVTU skeleton (one piece per rank plus the parallel header; ghost arrays come in M8), and the high-order pyramid fallback (vertices only, type 14, one warning). It adds the device conversion of GLL geometry to equispaced nodes for both writers, a host-level VTU reader for round trips and the VTK-written fixtures, and Python oracles (VTK, meshio) for the acceptance tests.

## Findings from planning (fed ADR-0024)

- **vtkIntegrateAttributes is piecewise linear on Lagrange cells** (checked with VTK 9.7.0 in Homebrew Python).
  - Both `vtkIntegrationLinearStrategy` and `vtkIntegrationGaussianStrategy` subdivide cells 68–73 into linear sub-cells through their nodes. The Gaussian strategy warns "Cell type (69) is not yet supported" and falls back.
  - A curved P2 triangle integrates to 0.600, not the exact 0.633. P2 Lagrange curves are skipped ("Odd number of points").
  - The bullet "integrated volume or area of P2 and P3 meshes equals `measure` to 10^−10" can therefore hold only where every cell is affine.
  - `vtkCell::EvaluateLocation` on a Lagrange cell is exact: on the curved tri6 at (1/4, 1/4) it matches the P2 basis to machine precision.
  - **Maintainer's choice (2026-10-27): affine + EvaluateLocation** (question 7).
- **No `.venv` exists** in any checkout.
  - `vtk` and `meshio` are not installed in the Python interpreters that run the tests. Homebrew's `python3` has vtk 9.7.0 but no meshio.
  - docs/dev-environment.md records vtk 9.7.1 and meshio 5.3.5, but nothing pins them.
  - Hosted CI (`ci.yml`, cpu and vulkan jobs) has no Python packages.
- **No VTK-written fixture exists**, although ADR-0008 assigns VTK-written prisms at p = 3, 5 and 6 to M5. `vtk_to_internal` covers every cell at any p and returns `NotInFormat` for pyramids with p ≥ 2.
- **No node-family conversion exists.**
  - `GmshWriter` rejects GLL (`gridcl/src/gmsh.rs:333`).
  - The interpolation can reuse `physical_points_block` (`gridcl-geometry/src/points_jac.rs:31`, the GeomFactors kernel) at the equispaced lattice, through `PointSet::new`, which is crate-private. The conversion therefore belongs in gridcl-geometry.
- **No cell or point data concept** exists anywhere; Listing B13 has only `vtu`, `lagrange`, `write` and `write_any`.
- `GmshWriter`'s `download` (`gridcl/src/gmsh.rs:306`) is the pattern for copying a mesh to the host: nodes plus origin in f64, dofmaps, cell blocks and `NodeFamily`.
- The capturing logger for warning tests is private to `gridcl/src/gmsh.rs` tests.

## Planned public API and rules (ADR-0024, accepted)

As in M3, M3s and M4, this fixes what ADR-0024 decides before T0.

- **Crate split (question 2).** Following ADR-0022:
  - `gridcl_io::vtk` holds the host side: the file model, the cell-type table (A.8), conversion from a host mesh description, the VTU/PVTU XML writer and the VTU parser.
  - `gridcl::vtk` holds `VtkWriter`, which copies a `Mesh` to the host.
  - The prelude exports `VtkWriter` (Listing B13 uses it unqualified) and the module `vtk`.
  - gridcl-io gains `flate2` (zlib, `rust_backend`, a workspace dependency) and a crate-private base64 encoder and decoder (question 11).
- **gridcl-io, `vtk` module:**
  - `pub fn vtk_cell_type(cell: CellType, degree: u32, lagrange: bool) -> u8` (A.8; pyramids with p ≥ 2 → 14).
  - `pub struct VtkMesh { gdim, nodes: Vec<f64> /* [node][gdim], origin added */, blocks: Vec<VtkCellBlock> }`, `VtkCellBlock { cell, degree, nodes: Vec<u32> /* A.5 order */ }`.
  - `pub enum DataValues { F32(Vec<f32>), F64(Vec<f64>), I32(Vec<i32>), U32(Vec<u32>), I64(Vec<i64>), U8(Vec<u8>) }`, `pub struct DataArray { name: String, components: usize, values: DataValues }`.
  - `pub struct VtuFile { points: DataValues /* F32 or F64, [n][3] */, connectivity: Vec<i64>, offsets: Vec<i64>, types: Vec<u8>, point_data: Vec<DataArray>, cell_data: Vec<DataArray> }`.
  - `pub fn to_vtu(mesh: &VtkMesh, lagrange: bool, f32_points: bool) -> Result<(VtuFile, usize /* pyramids written linear */)>`.
  - `pub enum Binary { Appended, Base64 }`.
  - `VtuFile::write_to(&self, w: &mut dyn Write, binary: Binary, zlib: bool) -> Result<()>` writes `version="2.2"`, `header_type="UInt64"` and `byte_order="LittleEndian"`.
  - `pub fn write_pvtu(w: &mut dyn Write, pieces: &[String], like: &VtuFile) -> Result<()>` writes the array declarations of `like`.
  - `pub fn parse_vtu(bytes: &[u8]) -> Result<VtuFile>`:
    - reads ASCII, inline base64, and appended raw or base64 data;
    - with or without zlib, and with UInt32 or UInt64 headers;
    - errors are `GridError::Parse { format: "VTU", .. }`;
    - host-level only: there is no mesh-level `vtk::read` (question 10).
- **gridcl-geometry (question 8):** `pub fn equispaced_nodes<F: Real, G: DeviceGrid<F>>(grid: &G) -> Result<DeviceBuffer<F>>` returns the node array with the same numbering and length, with every GLL block's nodes replaced by the equispaced interpolant.
  - Per GLL block, the existing physical-points kernel evaluates at `lagrange_points(cell, p, Equispaced)`.
  - Each node takes its value from its first occurrence in flat (block, cell, local) order: stable sort, then `unique_by_key` with its allowed count read, then gather. The result is deterministic and uses no atomics.
  - Equispaced blocks are copied unchanged.
  - No new kernel family goes on the candidate list.
- **gridcl, `vtk` (questions 3–6, 9):**
  - `VtkWriter<'a>`:
    - `vtu(path)` writes `path`, with `.vtu` appended if missing;
    - `pvtu(path)` writes `<stem>.pvtu` plus `<stem>_<rank>.vtu`;
    - `.lagrange(bool)` defaults to true, following A.8's writer column; false writes every cell linear, from its corner nodes;
    - `.base64(bool)` defaults to appended raw data; `.zlib(bool)` defaults to off;
    - `.point_data(name, &'a DeviceBuffer<T>, components)` and `.cell_data(name, &'a DeviceBuffer<T>, components)`, with `T: VtkScalar`, a sealed trait for f32, f64, i32 and u32;
    - `.write(&Mesh<F, TD, GD, C>)` and `.write_any(AnyMeshRef<'_, F, C>)`.
  - Point and cell data:
    - point data is indexed by geometry node, with length `num_nodes · components`;
    - cell data is indexed by flat cell index in block order, with length `num_cells · components`;
    - a wrong length gives `LengthMismatch`;
    - a second array with the same name in the same section replaces the first (builder semantics, no new `GridError` variant).
  - Points:
    - always all geometry nodes in node order, after `equispaced_nodes`, with the origin added in f64;
    - Float64 for f64 meshes, narrowed to Float32 for f32 meshes;
    - linear output leaves the non-vertex nodes unreferenced, so point data needs no remapping.
  - Pyramids with p ≥ 2 are written as type 14 from their five vertices, with one `log::warn!` per written file, only when `lagrange(true)`.
  - No automatic arrays: `vtkGhostType` and any origin-id arrays come with M8.
  - Ranks: `vtu` with more than one rank gives `NotYetImplemented("parallel VTU write (M8)")`. `pvtu` writes one piece per rank; with more than one rank it also gives `NotYetImplemented` until M8.
- **`GmshWriter`:** uses `equispaced_nodes`; the `UnsupportedNodeFamily` rejection is removed (ADR-0022 item 9).
- **gridcl-testing:**
  - `HostMesh::mapped(gdim_out, f: impl Fn(&[f64]) -> Vec<f64>)` applies a node map: affine images, and planar 2D meshes embedded in 3D.
  - A shared capturing logger, `gridcl_testing::log_capture`, if more than one test binary needs it.
- **Python oracle policy (question 12):**
  - Pins: `vtk==9.7.1` and `meshio==5.3.5` in `.venv`. `scripts/check-local-tools.sh` checks them, and the oracle script asserts them.
  - Tests find the interpreter through `GRIDCL_PYTHON`, else `<repo>/.venv/bin/python`.
  - A missing interpreter fails the test, unless `GRIDCL_SKIP_PYTHON=1` is set; then the test prints that it skipped.
  - CI's cpu and vulkan jobs install the pins.
  - Remote CUDA runs set `GRIDCL_SKIP_PYTHON=1`: the oracles are host-only, and Rust tests cover the device paths.
- **Acceptance wording (question 7, ADR-0024):** the integration bullet uses affine P2 and P3 meshes. A new curved bullet checks VTK's `EvaluateLocation` against gridcl's `physical_points` to 10^−10 (f64).

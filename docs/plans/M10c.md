## Scope summary

M10c re-derives the `[Cpu]` vector set of `vector-policy.toml` from records timed in interleaved rounds in two processes over the grid of vector sizes 1, 4, 8 and 16, blocks of 4, 16 and 64 KiB and both unit settings, on the three Cpu platforms. It applies the generic rule's fallback without the admission gate to all four sets, which also changes a few `[Gpu]` vector entries and per-degree choices of `degree-policy.toml` from the committed records (ADR-0065). It ends with the standing matrix under the new sets.

## Findings from planning

Read against main at 5b737c0.

1. **Rule.** `decide_generic::generic_rule` (`gridcl-bench/src/decide_generic.rs:139`) takes `t: Fn(K, usize, usize) -> f64` and requires a time for every candidate, member and size. Its fallback is the admitted configuration with the smallest worst case (`:194`). `decide_vector` (`:423`) and `decide_degree` (`:1047`) both call it, so the waiver reaches all four sets through one function.
2. **Records.** `member_times` (`:392`) keeps the last record of a configuration (`a later record ... replaces an earlier one`), so two processes' records would overwrite each other. `SweepRecord` (`record.rs:93`) has no seed and no round positions.
3. **Loader.** `load_m10_dir` (`record.rs:1356`) reads only `m10-*.json` (`m10c-` files are skipped by its prefix filter). `M10Data` (`:1336`) has no place for the grid records.
4. **Live policies in M10's history.** `candidates::vector_candidates` and `degree_candidates` include "the one the entry's own policy names" from the live `VECTOR_POLICY_TOML` and `DEGREE_POLICY_TOML` (`candidates.rs:49, 263`). M10's history tests read the live files: `m10_candidates_cover_every_kind_and_platform` (through `vector_candidates`), `tensor_cost_ratio_within_bound_or_reported` (`policy()` at `high_order_record.rs:393`), the candidate-set tests of `candidates.rs`. Once M10c changes either file, these tests would fail on M10's unchanged records. M10's TOMLs must be frozen as history first, as `history/*-pre-m10.toml` were in M10.
5. **Reports.** `policy_report` (`bin/policy_report.rs:92`) writes `vector-policy.toml` and the M10 tables between `M10_BEGIN_MARKER`/`M10_END_MARKER` (`report.rs:35`) from `decide_vector(&m10)`; `vectorization_report_lists_platform_ratios` checks the section against `render_m10_vector`. `high_order_report` does the same for `degree-policy.toml` and M10's high-order section. The M10 rows have no cause column; a fallback row only contains "worst case".
6. **Probe code.** `probe_cpu_widths.rs` and `scripts/probe-cpu-widths.sh` (uncommitted, worktree `t3/cpu-vector-width-probe`) implement the interleaved rounds: per entry, every (member scalar, size, configuration) is warmed up, checked and calibrated (`protocol::measure` with zero runs), then five rounds each time one batched run of every slot in an order shuffled by splitmix64 from the seed; records carry `seed` and `positions`. T3 builds the gridcl-bench mode from it.
7. **Grid and baseline.** Every `[Cpu]` baseline (n = 1 at the old CpuSimd128 tile, block and units, `candidates.rs:188`) lies in the grid: CpuSimd128's GeomFactors tile is 4 at both sizes, its blocks are 4, 16 or 64 KiB. The CPU runtime offers n = 16 on all three platforms (probe); a requested width the plan caps runs at `vector_size_ran`, as in M10.
8. **Entries.** `candidate_kinds` gives 21 `[Cpu]` entries with a typed scalar: 13 four-byte (Fill, Copy, Reduce, ScanTile, SortDigits, Gather, Pack, TopologyKeys, PermutationInfo, EVector, GeomFactors, PullBack, Scalar) and 8 eight-byte (Fill, Reduce, Gather, Pack, EVector, GeomFactors, PullBack, Scalar). The other five 8-byte entries have no type and keep their default.
9. **Degree records and the new vector set.** M10's degree records ran under M10's vector policy. A new `[Cpu]` vector size for EVector, GeomFactors or PullBack changes what the CPU degree kernels run; ADR-0065 re-derives `degree-policy.toml` from the committed records only. See question 6.

## Review
